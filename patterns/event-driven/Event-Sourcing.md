# Event Sourcing

## Problem

In traditional CRUD-based systems, the database reflects only the current state of an entity. When an order is updated from "pending" to "shipped," the previous state is overwritten. This is operationally convenient but loses the history of what happened and why. Audit requirements often retrofit logging after the fact, producing incomplete or inconsistently structured records. Debugging production data anomalies is difficult when the only available information is the current state — there is no way to reconstruct how the system arrived there.

More fundamentally, current-state-only systems make certain categories of queries expensive or impossible: temporal queries ("what did the order look like at 3 PM yesterday?"), aggregate projections from past state ("total revenue generated by orders that were eventually cancelled"), and behavioral analytics ("how many orders go through a re-processing step before shipping?").

## Solution

Event Sourcing models system state as an ordered, immutable sequence of events. Rather than storing the current state of an entity, the system stores every event that has affected that entity since its creation. The current state is derived by replaying the event sequence from inception. Events are facts — things that happened — and are never modified or deleted.

The append-only event log becomes the authoritative source of truth. Projections (also called read models or views) are derived from the event log for query purposes and can be rebuilt from scratch at any time by replaying events. This enables temporal queries, retroactive projections, and event stream replay for debugging or migration.

On Azure, event sourcing is implemented using Azure Cosmos DB (as the event store, leveraging its Change Feed), Azure Service Bus or Event Hubs (for event stream distribution), and Azure Functions or Azure Stream Analytics (for projection building).

## When to Use

- Use when audit history is a first-class requirement — financial systems, healthcare records, regulatory compliance domains.
- Use when you need temporal queries ("point-in-time" state reconstruction).
- Use when the business domain has complex state transitions that benefit from explicit event modeling (order lifecycle, approval workflows, inventory tracking).
- Use when you need to support multiple independent read projections from the same underlying data (CQRS complement).
- Avoid when the domain is simple CRUD with no meaningful state transition history — event sourcing adds significant complexity for marginal benefit.
- Avoid when the team is new to event-driven design — event sourcing is a commitment that affects every aspect of the development model. Start with simpler event-driven patterns.
- Avoid when event volumes are extremely high and replay times make the pattern impractical without expensive snapshotting infrastructure.

## Azure Implementation

### Cosmos DB as Event Store

Cosmos DB with the NoSQL API provides an effective event store: partition by aggregate ID, sort by event sequence number, and use the Change Feed to distribute events to consumers.

```csharp
// Event store schema — each document is one event
public class OrderEvent
{
    [JsonPropertyName("id")]
    public string Id { get; init; } = Guid.NewGuid().ToString();

    // Partition key = aggregate ID (orderId)
    [JsonPropertyName("aggregateId")]
    public string AggregateId { get; init; } = default!;

    [JsonPropertyName("aggregateType")]
    public string AggregateType { get; init; } = "Order";

    [JsonPropertyName("eventType")]
    public string EventType { get; init; } = default!;

    [JsonPropertyName("eventVersion")]
    public int EventVersion { get; init; }

    [JsonPropertyName("sequenceNumber")]
    public long SequenceNumber { get; init; }

    [JsonPropertyName("occurredAt")]
    public DateTimeOffset OccurredAt { get; init; } = DateTimeOffset.UtcNow;

    [JsonPropertyName("causedBy")]
    public string CausedBy { get; init; } = default!;  // userId or system ID

    [JsonPropertyName("correlationId")]
    public string CorrelationId { get; init; } = default!;

    [JsonPropertyName("payload")]
    public JsonElement Payload { get; init; }
}
```

### Append-Only Event Persistence

Use Cosmos DB optimistic concurrency (ETag) to prevent concurrent writes from overwriting events. Conditional writes enforce the event ordering invariant:

```csharp
public class CosmosEventStore
{
    private readonly CosmosClient _client;
    private readonly Container _container;

    public async Task AppendEventsAsync(string aggregateId, IReadOnlyList<OrderEvent> events,
        long expectedVersion)
    {
        // Verify current sequence number matches expectation (optimistic concurrency)
        var query = new QueryDefinition(
            "SELECT VALUE MAX(e.sequenceNumber) FROM e WHERE e.aggregateId = @id")
            .WithParameter("@id", aggregateId);

        var currentVersion = await _container.GetItemQueryIterator<long?>(query,
            requestOptions: new QueryRequestOptions { PartitionKey = new PartitionKey(aggregateId) })
            .ReadNextAsync().ContinueWith(t => t.Result.FirstOrDefault() ?? 0);

        if (currentVersion != expectedVersion)
            throw new ConcurrencyException(
                $"Expected version {expectedVersion} but found {currentVersion} for aggregate {aggregateId}");

        // Batch append all events
        var batch = _container.CreateTransactionalBatch(new PartitionKey(aggregateId));
        foreach (var ev in events)
            batch.CreateItem(ev);

        var response = await batch.ExecuteAsync();
        if (!response.IsSuccessStatusCode)
            throw new EventStoreException($"Failed to append events: {response.StatusCode}");
    }

    public async IAsyncEnumerable<OrderEvent> LoadEventsAsync(string aggregateId,
        long fromSequence = 0)
    {
        var query = new QueryDefinition(
            "SELECT * FROM e WHERE e.aggregateId = @id AND e.sequenceNumber >= @from ORDER BY e.sequenceNumber")
            .WithParameter("@id", aggregateId)
            .WithParameter("@from", fromSequence);

        var iterator = _container.GetItemQueryIterator<OrderEvent>(query,
            requestOptions: new QueryRequestOptions { PartitionKey = new PartitionKey(aggregateId) });

        while (iterator.HasMoreResults)
            foreach (var ev in await iterator.ReadNextAsync())
                yield return ev;
    }
}
```

### Aggregate Reconstruction from Events

The Order aggregate reconstructs its state by applying events in sequence:

```csharp
public class Order
{
    public string OrderId { get; private set; } = default!;
    public string CustomerId { get; private set; } = default!;
    public OrderStatus Status { get; private set; }
    public decimal TotalAmount { get; private set; }
    public List<OrderItem> Items { get; private set; } = new();
    public long Version { get; private set; }

    private readonly List<OrderEvent> _pendingEvents = new();

    public static async Task<Order> RehydrateAsync(string orderId, IEventStore store)
    {
        var order = new Order();
        await foreach (var ev in store.LoadEventsAsync(orderId))
            order.Apply(ev);
        return order;
    }

    private void Apply(OrderEvent ev)
    {
        switch (ev.EventType)
        {
            case "OrderCreated":
                var created = ev.Payload.Deserialize<OrderCreatedPayload>()!;
                OrderId    = created.OrderId;
                CustomerId = created.CustomerId;
                Status     = OrderStatus.Pending;
                Items      = created.Items;
                TotalAmount = created.TotalAmount;
                break;

            case "OrderConfirmed":
                Status = OrderStatus.Confirmed;
                break;

            case "OrderShipped":
                Status = OrderStatus.Shipped;
                break;

            case "OrderCancelled":
                Status = OrderStatus.Cancelled;
                break;
        }
        Version = ev.SequenceNumber;
    }

    public void Confirm(string confirmedBy, string correlationId)
    {
        if (Status != OrderStatus.Pending)
            throw new InvalidOperationException($"Cannot confirm order in status {Status}");

        var ev = new OrderEvent
        {
            AggregateId   = OrderId,
            EventType     = "OrderConfirmed",
            SequenceNumber = Version + 1,
            CausedBy      = confirmedBy,
            CorrelationId = correlationId,
            Payload       = JsonSerializer.SerializeToElement(new { ConfirmedBy = confirmedBy })
        };

        _pendingEvents.Add(ev);
        Apply(ev);
    }
}
```

### Cosmos DB Change Feed → Projection Builder

Use the Cosmos DB Change Feed to stream new events to projection builders via Azure Functions:

```csharp
[Function("OrderProjectionBuilder")]
public async Task Run(
    [CosmosDBTrigger(
        databaseName: "EventStore",
        containerName: "OrderEvents",
        Connection = "CosmosDB",
        LeaseContainerName = "leases",
        CreateLeaseContainerIfNotExists = true)]
    IReadOnlyList<OrderEvent> events)
{
    foreach (var ev in events)
    {
        // Update the read model projection in a separate Cosmos DB container
        switch (ev.EventType)
        {
            case "OrderCreated":
                await _projectionStore.UpsertOrderSummaryAsync(new OrderSummary
                {
                    OrderId    = ev.AggregateId,
                    CustomerId = ev.Payload.GetProperty("customerId").GetString(),
                    Status     = "Pending",
                    CreatedAt  = ev.OccurredAt
                });
                break;

            case "OrderShipped":
                await _projectionStore.UpdateOrderStatusAsync(ev.AggregateId, "Shipped");
                break;
        }
    }
}
```

### Snapshotting for Long-Lived Aggregates

When an aggregate accumulates hundreds or thousands of events, replay time becomes significant. Implement periodic snapshots to allow rehydration from the most recent snapshot + subsequent events:

```csharp
public class SnapshotStore
{
    public async Task SaveSnapshotAsync(string aggregateId, Order order)
    {
        var snapshot = new OrderSnapshot
        {
            Id          = $"{aggregateId}-snapshot",
            AggregateId = aggregateId,
            Version     = order.Version,
            State       = JsonSerializer.SerializeToElement(order),
            SnapshotAt  = DateTimeOffset.UtcNow
        };
        await _snapshotContainer.UpsertItemAsync(snapshot, new PartitionKey(aggregateId));
    }
}
```

## Key Considerations

**Immutability is Non-Negotiable:** Event sourcing's guarantees rest entirely on the append-only, immutable nature of the event log. Any process that modifies or deletes events corrupts the store. Implement Cosmos DB resource locks or RBAC to prevent delete operations on the event container. Treat the event store as write-once infrastructure.

**Event Schema Versioning:** Events are permanent records. When the business domain evolves and the shape of an event needs to change, you cannot update old events in place. Implement event upcasting — a versioned transformation applied during event loading that converts old event versions to the current schema before passing them to the aggregate's Apply method. Store `eventVersion` on every event document from day one.

**Projection Consistency:** Projections built from the Change Feed are eventually consistent with the event store. If a consumer reads the projection immediately after writing an event, they may not see the event's effect yet. Design your UI and API layer to tolerate this: return the updated state from the command handler directly, or implement a "wait for version" polling mechanism.

**Replay Performance:** Event replay performance is a function of event volume per aggregate and event store query performance. Cosmos DB partition-scoped queries over ordered sequence numbers are efficient, but aggregates with thousands of events will still take time to rehydrate. Snapshot strategy should target rehydration times under 100ms for interactive workloads.

**GDPR and Data Deletion:** Event sourcing is in tension with "right to be forgotten" requirements — events are immutable. Resolve this with "crypto-shredding": encrypt sensitive event payload fields with a per-user encryption key stored separately. Deleting the encryption key renders the sensitive data unreadable without modifying the event log.
